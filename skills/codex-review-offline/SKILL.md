# /codex-review-offline — офлайн код-ревью правок 1С через Codex (read-only)

Скилл для проектов, которые представляют собой выгрузку Конфигуратора (XML) без git: «до» берётся из
папки-бэкапа, сделанной перед правкой. Codex работает **только на чтение**, на локальной копии файлов,
пользовательский конфиг и MCP отключены (`--ignore-user-config`), проект не изменяется.

Ниже `<SKILL_DIR>` — каталог этого скилла, `<BACKUP_ROOT>` — каталог, где проект хранит бэкапы
(задаётся в CLAUDE.md проекта; если не задан — спросить пользователя).

## Разбор аргументов

- Первый токен — **путь к файлу** относительно корня текущего проекта (например
  `Reports/МойОтчет/Ext/ObjectModule.bsl`) либо **имя объекта** (тогда искать через `Glob`
  `**/<Имя>/**/*.bsl` от корня проекта). Можно перечислить несколько файлов через пробел/запятую.
  Если по имени объекта нашлось несколько кандидатов (например `ObjectModule.bsl` и модуль формы) —
  уточнить через `AskUserQuestion`, какие брать.
- `--all` — ревьюить файл(ы) целиком, не только изменения. По умолчанию (без флага) — фокус на правках:
  маркерах авторских правок из CLAUDE.md проекта (например `//Начало: <автор> … //Конец` /
  `// убрано <автор>`) и на diff относительно бэкапа.
- `--effort low|medium|high` — усилие рассуждения Codex, по умолчанию `medium`. `low` — для очень больших
  файлов (1800+ строк) или когда нужен быстрый ответ; `high` — для сложной логики (на практике даёт более
  точные находки, чем `medium`).
- `--backup <папка>` — конкретная папка бэкапа внутри `<BACKUP_ROOT>`, если нужно сравнить не с
  последним бэкапом. По умолчанию — **самый свежий** бэкап текущего проекта (бэкап делается непосредственно
  перед последней правкой, значит это и есть состояние «до»).
- Остальной свободный текст — дополнительный фокус ревью (конкретные сценарии проверки).

## Шаг 1. Определить проект и бэкап

- Имя проекта = имя каталога текущего рабочего каталога.
- Найти бэкапы: `<BACKUP_ROOT>\<ИмяПроекта>_*` — папки с суффиксом `_YYYYMMDD` и опционально `_N`.
  Без `--backup` взять самую свежую по дате изменения папки.
- Если бэкапов для проекта нет вообще — сообщить пользователю и предложить ревью без диффа (`--all`-режим
  по факту, явно это пометить в промпте).

```powershell
Get-ChildItem "<BACKUP_ROOT>" -Directory -Filter "<ИмяПроекта>_*" | Sort-Object LastWriteTime -Descending | Select-Object -First 5 Name
```

## Шаг 2. Рабочий каталог

`<scratchpad>\codex-review-<ASCII-слаг>\` — ASCII-имя обязательно (кириллица в имени каталога мешает Codex
читать файлы). Слаг — транслит или короткое смысловое имя объекта.

## Шаг 3. Материалы

Для каждого файла из Шага 1:

1. Скопировать **текущую** версию в `<workdir>\<ИмяФайла>` (тем же базовым именем — `Module.bsl`,
   `ObjectModule.bsl` и т.п.).
2. Найти этот же файл в выбранном бэкапе (тот же относительный путь от корня проекта). Если файла там нет —
   значит он новый после бэкапа: предупредить пользователя, дифф для него не строится, ревьюить целиком
   (для нового объекта-копии полезен дифф с объектом-образцом).
3. Нормализовать оба варианта (бэкап и текущий) к LF и построить unified diff. Без `diff`/`tr` в системе
   подойдёт `git diff --no-index` (git-репозиторий для этого не нужен):

```powershell
[IO.File]::WriteAllText("$w\b.txt", [IO.File]::ReadAllText("<бэкап>\<ОтносительныйПуть>").Replace("`r",""))
[IO.File]::WriteAllText("$w\n.txt", [IO.File]::ReadAllText("<текущий>\<ОтносительныйПуть>").Replace("`r",""))
git diff --no-index --no-color -U4 "$w\b.txt" "$w\n.txt" | Out-File "$w\diff_<ИмяФайла>.txt" -Encoding utf8
```

4. При необходимости — положить рядом вспомогательные фрагменты неизменённого кода, от которого зависит
   логика правки (например начало вызываемой функции общего модуля), отдельными файлами с говорящими именами.
   Для правок метаданных и форм — диффы их XML тем же способом.

## Шаг 4. context.md

Без контекста ревью формальное. Порядок подготовки:

1. Проверить заметки проекта (например `Memory Bank.md` в корне) — если там уже есть раздел про этот
   объект/механику (структура регистров, порядок вызовов, известные подводные камни, история правок) —
   взять оттуда, это приоритетный источник.
2. Дополнить тем, чего в заметках нет: что именно и зачем изменено в этой правке, включая историю
   неудачных редакций, если она была. Если решающей информации не хватает — коротко спросить пользователя
   (не блокировать весь скилл, спросить только недостающее).
3. Записать всё в `<workdir>\context.md` — **в UTF-8 с BOM**: Codex читает файлы через `Get-Content`
   Windows PowerShell, и без BOM кириллица превращается в мусор.

## Шаг 5. _prompt.txt

Записать в `<workdir>\_prompt.txt` (UTF-8) по шаблону:

```
Ты — старший ревьюер кода 1С:Предприятие 8.3 (BSL, язык запросов, управляемые формы).

В ТЕКУЩЕМ рабочем каталоге лежат <перечислить файлы: Module.bsl, diff_Module.txt, context.md, ...>.
Прочитай их с диска и проведи ревью ВНЕСЁННЫХ ИЗМЕНЕНИЙ.

ОБЛАСТЬ РЕВЬЮ:
<без --all: "Только правки — см. diff_*.txt и маркеры правок <формат маркеров>. Остальной код существующий, вне задачи.">
<с --all: "Файл(ы) целиком.">

КОНТЕКСТ ПРОЕКТА: см. context.md.

ЧТО ИСКАТЬ (по важности):
1. Ошибки, ломающие выполнение: синтаксис запроса и многострочных литералов BSL, поля неограниченной длины
   в соединениях/индексах/РАЗЛИЧНЫЕ, ошибки типов, контекст вызова (клиент/сервер), работа с Соответствие
   и регистр имён колонок, корректность НаборЗаписей.Отбор по измерениям и Записать(Истина).
2. Логика: <конкретные сценарии из context.md / доп. фокуса пользователя — повторная загрузка, пустые
   значения ключа, границы периода, влияние на соседние ветки того же механизма>.
3. Производительность: число обращений к СУБД, использование индексов, размер временных таблиц.
4. Транзакционность: что останется в данных при обрыве в середине.

ФОРМАТ ОТВЕТА (на русском):
- Находки по критичности: Высокая / Средняя / Низкая.
- Для каждой: файл и номер строки, суть в одном предложении, конкретный сценарий сбоя, точечная правка.
- Возможные ложные срабатывания помечай «(проверить: …)».
- Не предлагай переписывание модуля целиком.
- Если критичных проблем нет — так и напиши.

ОГРАНИЧЕНИЯ: только анализ. Ничего не создавай и не изменяй на диске.

```

## Шаг 6. Запуск

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>\scripts\codex-review.ps1" `
    -WorkDir "<workdir>" -PromptFile "<workdir>\_prompt.txt" -Effort <effort>
```

Скрипт сам находит свежий `codex.exe`, гоняет `codex exec --ignore-user-config --sandbox read-only`
(MCP выключен) и пишет ответ в `<workdir>\_review.md`. На `medium`/`high` ревью занимает 2–5+ минут — запускай
в фоне (`run_in_background: true`), не жди в foreground. Не перенаправляй вывод через `2>&1` в Windows
PowerShell: строки Codex в stderr превращаются в `NativeCommandError` (`*> лог-файл` — можно).

**Песочница Windows.** Если в `config.toml` стоит `[windows] sandbox = "elevated"`, Codex блокирует любой
подпроцесс, даже чтение файлов («blocked by policy»), и `--sandbox read-only` тут ни при чём. Раннер поэтому
всегда передаёт `-c 'windows.sandbox="unelevated"'`. Запрет записи (`read-only`) при этом сохраняется.
PowerShell внутри песочницы идёт в Constrained Language Mode — Codex иногда ловит
`MethodInvocationNotSupportedInConstrainedLanguage` на сложных командах, но сам переходит на простые и
доводит ревью до конца.

## Шаг 7. Возврат результата

- Прочитать `<workdir>\_review.md`, вернуть находки пользователю **дословно**.
- Шапка: объект(ы), база сравнения (какой бэкап или «без диффа»), область (marked/`--all`), effort, время.
- Обязательное предупреждение: **находки не верифицированы**. Codex видит только переданные файлы — не
  знает структуру метаданных за пределами `context.md`, не видит данные, не может выполнить запрос.
  Перед правками:
  1. проверить каждую находку фактами (метаданные, соседний код, исходники БСП/типовой конфигурации, реальные данные);
  2. отделить реальные дефекты от задуманного поведения — искать рядом авторские комментарии;
  3. сценарии проверять на реальных данных (посчитать строки/документы/суммы), а не рассуждением;
  4. доложить раздельно: что подтвердилось, что снято фактами и почему, что оставлено осознанно.
- Если находки подтвердились и правки внесены — записать вывод в заметки проекта.
- Ничего в проекте не менять.

## Типичные ошибки при подготовке

- Кириллица в имени рабочего каталога — Codex не читает файлы.
- `context.md` без BOM — Codex читает его как ANSI и видит мусор вместо кириллицы.
- Дифф, снятый без нормализации CRLF/LF, — весь файл выглядит изменённым, ревью уходит в пустоту.
- Передан только изменённый файл без диффа — Codex не понимает, где граница правки, ревьюит весь модуль.
- Промпт передан аргументом PowerShell — кириллица превращается в мусор (промпт только файлом).
- Не описана механика вокруг правки в context.md — находки получаются общими и бесполезными.

## Окружение (CRLF/BOM)

`awk`/`sed` в Git Bash при перезаписи файла теряют `\r`: CRLF → LF/смешанный. Файлы выгрузки 1С — UTF-8 с BOM
и CRLF; `Template.xml` макетов хранится без финального перевода строки. Проверка: число `\r` должно равняться
числу `\n`.
