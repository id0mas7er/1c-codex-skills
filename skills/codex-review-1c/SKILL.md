# /codex-review-1c — код-ревью правок 1С через Codex (read-only)

Codex — исполнитель, Claude — проверяющий. Codex **только читает** исходники (песочница `read-only`,
пользовательский конфиг и MCP отключены `--ignore-user-config`) и возвращает находки. Находка не считается
дефектом, пока Claude не подтвердит её по коду, метаданным или данным.

Два режима с общим порядком работы:

| Режим | Для каких проектов | Что видит Codex |
|---|---|---|
| **edt** | проекты 1C:EDT (`<проект>/DT-INF/PROJECT.PMF`, `src/Configuration/Configuration.mdo`) | папки указанных объектов прямо в рабочей области EDT |
| **offline** | выгрузка Конфигуратора (XML) без git | локальную копию файлов, `diff_*.txt` относительно папки-бэкапа, `context.md` |

Ниже `<SKILL_DIR>` — каталог этого скилла, `<scratchpad>` — временный каталог сессии.

## Аргументы

- Пути / объекты — один или несколько:
  - путь из дерева EDT с разделителями `→`, `->`, `/`, `\` (например `Документы→МойДокумент→Формы→ФормаДокумента`,
    `ВнешниеОбработки→Отчеты→МойОтчет`);
  - путь к файлу относительно корня проекта (`Reports/МойОтчет/Ext/ObjectModule.bsl`);
  - голое имя объекта (`МойОтчет`).
  Пути с пробелами и кириллицей — в кавычках.
- `--mode edt|offline` — явно задать режим (иначе определяется автоматически, см. Шаг 0).
- `--all` — ревьюить объекты целиком. По умолчанию — только правки: маркеры авторских правок из CLAUDE.md
  проекта (например `// ++{ПРЕФИКС} … // --{ПРЕФИКС}` или `//Начало: <автор> … //Конец`) и, в режиме offline, diff
  относительно бэкапа.
- `--effort low|medium|high` — усилие Codex, по умолчанию `medium`. `low` — очень большие файлы (1800+ строк) или
  быстрый ответ; `high` — сложная логика, запросы, правки на стыке объектов (находки точнее, чем на `medium`).
- `--backup <папка>` — только offline: конкретная папка бэкапа вместо самой свежей.
- `--iter <путь>` — журнал ревью `review.md`, если он лежит не там, где его ищет Шаг 3.
- Остальной свободный текст — дополнительный фокус ревью (конкретные сценарии проверки).

Если не передан ни один путь — не ревьюить «всё подряд»: спросить, какой объект смотреть.

## Шаг 0. Режим

По порядку, первое сработавшее правило:

1. Задан `--mode` — он.
2. Аргумент содержит `→` / `->` (путь из дерева EDT) — **edt**.
3. В текущем корне или его подпапках первого уровня есть `DT-INF/PROJECT.PMF` — **edt**.
4. В корне проекта есть `Configuration.xml`, у объектов — каталоги `Ext/` — **offline**.
5. Иначе (или сработали признаки обоих режимов) — спросить через `AskUserQuestion`.

```powershell
Get-ChildItem -Path . -Filter PROJECT.PMF -Recurse -Depth 2 -ErrorAction SilentlyContinue | Select-Object -First 3 FullName
Test-Path .\Configuration.xml
```

## Шаг 1. Что ревьюить

### Режим edt

Корень рабочей области EDT — каталог, где лежат EDT-проекты (подпапки с `src/`). Обычно это корень текущего
проекта; можно задать переменной `EDT_WORKSPACE` или параметром `--workspace`.

```bash
node "<SKILL_DIR>/scripts/edt-resolve.mjs" --workspace "<корень>" "<путь1>" "<путь2>"
```

- stdout — абсолютные пути папок объектов, это и есть цель ревью.
- Ненайденные пути (stderr) показать пользователю и уточнить — не подставлять наугад.
- Имя нашлось в нескольких проектах (основная конфигурация и расширение, конфигурация и внешний отчёт) —
  показать варианты и спросить, какой ревьюить (или оба, если пользователь так просил). Имя проекта в
  пути (`МойПроект→Документы→X`) сужает поиск до этого проекта.

### Режим offline

1. Файлы: по пути — как есть; по имени объекта — `Glob` `**/<Имя>/**/*.bsl` от корня проекта. Несколько
   кандидатов (`ObjectModule.bsl` и модуль формы) — уточнить через `AskUserQuestion`.
2. Бэкап: `<BACKUP_ROOT>` — каталог бэкапов проекта (задаётся в CLAUDE.md проекта; если не задан — спросить).
   Имя проекта = имя текущего каталога; бэкапы — `<BACKUP_ROOT>\<ИмяПроекта>_*` (суффикс `_YYYYMMDD`,
   опционально `_N`). Без `--backup` — самый свежий: бэкап делается перед последней правкой, это и есть «до».
   Бэкапов нет — сообщить и предложить ревью без диффа (по факту `--all`, явно пометить в промпте).

```powershell
Get-ChildItem "<BACKUP_ROOT>" -Directory -Filter "<ИмяПроекта>_*" | Sort-Object LastWriteTime -Descending | Select-Object -First 5 Name
```

## Шаг 2. Рабочий каталог и материалы

`<workdir>` = `<scratchpad>\codex-review-<ASCII-слаг>\` — **ASCII-имя обязательно** (в режиме offline Codex
работает в этом каталоге, и кириллица в его имени мешает читать файлы). Слаг — транслит или короткое имя объекта.

### Режим edt

В `<workdir>` кладётся только `_prompt.txt` (Шаг 4); Codex читает объекты на месте, в рабочей области EDT.
Если для понимания правки нужен контекст, которого нет в коде (что и зачем менялось, спека задачи), — указать в
промпте путь к спеке/заметкам проекта, а не пересказывать.

### Режим offline

Для каждого файла:

1. Скопировать **текущую** версию в `<workdir>\<ИмяФайла>` (тем же базовым именем).
2. Найти этот же файл в бэкапе (тот же относительный путь). Нет в бэкапе — файл новый: предупредить, дифф не
   строить, ревьюить целиком (для объекта-копии полезен дифф с объектом-образцом).
3. Нормализовать обе версии к LF и построить unified diff (git-репозиторий не нужен):

```powershell
[IO.File]::WriteAllText("$w\b.txt", [IO.File]::ReadAllText("<бэкап>\<ОтносительныйПуть>").Replace("`r",""))
[IO.File]::WriteAllText("$w\n.txt", [IO.File]::ReadAllText("<текущий>\<ОтносительныйПуть>").Replace("`r",""))
git diff --no-index --no-color -U4 "$w\b.txt" "$w\n.txt" | Out-File "$w\diff_<ИмяФайла>.txt" -Encoding utf8
```

4. При необходимости — рядом вспомогательные фрагменты неизменённого кода, от которого зависит правка
   (например начало вызываемой функции общего модуля), файлами с говорящими именами. Правки метаданных и форм —
   диффы их XML тем же способом.
5. `context.md` — без контекста ревью формальное:
   - сначала заметки проекта (например `Memory Bank.md`): структура регистров, порядок вызовов, известные подводные
     камни, история правок — приоритетный источник;
   - дополнить тем, чего там нет: что и зачем изменено в этой правке, включая неудачные редакции. Не хватает
     решающей информации — коротко спросить пользователя только недостающее;
   - сохранить **в UTF-8 с BOM**: Codex читает файлы через `Get-Content` Windows PowerShell, без BOM кириллица
     превращается в мусор.

## Шаг 3. Журнал ревью (повторный прогон)

Codex между запусками ничего не помнит: без подсказки второй проход повторит прежние замечания или пропустит
непочиненное. Поэтому Claude ведёт журнал `review.md` — находка, уровень, место, итерация, статус
(`открыто` / `исправлено (итерация N)` / `отклонено: <причина>`). Журнал ведёт Claude по ответу Codex; Codex его
не правит.

Где искать: `--iter <путь>`; иначе — место, заданное в CLAUDE.md проекта (например папка задачи/спеки);
иначе `<workdir>\review.md`. Журнала нет — первая итерация, в промпт ничего не добавлять. Есть — добавить в промпт:

```
Ранее по этому артефакту уже выдавались замечания, журнал: <путь к review.md>.
Прочитай его. Сначала пройди по каждой находке со статусом «открыто» и вынеси вердикт:
исправлено / не исправлено / исправлено частично — проверяя по ТЕКУЩЕМУ коду, а не по описанию находки.
Затем отдельным разделом — новые находки, если появились.
Находки со статусом «исправлено» и «отклонено» заново не выдавай.
```

В режиме offline положить копию журнала в `<workdir>` (Codex видит только его) и сослаться на неё.

Отклонённую находку из журнала не удалять — оставить с причиной, иначе Codex выдаст её снова. Статус меняется
только по вердикту повторного прогона, а не по словам «исправил».

## Шаг 4. _prompt.txt

Записать `<workdir>\_prompt.txt` (UTF-8). Промпт — только файлом: аргументом командной строки кириллица ломается.

```
Ты — старший ревьюер кода 1С:Предприятие 8.3 (BSL, язык запросов, управляемые формы, метаданные).

<edt:     Проведи ревью ТОЛЬКО этих объектов (папки в рабочей области EDT): <перечислить пути из Шага 1>.
          Регламент проекта — <путь к CLAUDE.md>; контекст задачи — <путь к спеке/заметкам, если есть>.
          Не читай целиком *.mxlx и *.dcs, если вопрос не о макете — они большие и для ревью кода не нужны.>
<offline: В ТЕКУЩЕМ рабочем каталоге лежат <Module.bsl, diff_Module.txt, context.md, ...>.
          Прочитай их с диска. Контекст проекта — context.md.>

ОБЛАСТЬ РЕВЬЮ:
<без --all: "Только правки — <offline: см. diff_*.txt и> маркеры правок <формат маркеров из CLAUDE.md>.
             Остальной код существующий, вне задачи.">
<с --all:   "Объекты/файлы целиком.">

ЧТО ИСКАТЬ (по важности):
1. Ошибки, ломающие выполнение: синтаксис запроса и многострочных литералов BSL (удвоение кавычек), поля
   неограниченной длины в соединениях/индексах/РАЗЛИЧНЫЕ, ПРЕДСТАВЛЕНИЕ() в УПОРЯДОЧИТЬ ПО, подзапросы и
   В ИЕРАРХИИ в выражении группировки, сигнатуры виртуальных таблиц (Остатки, ОборотыДтКт, СрезПоследних,
   ДвиженияССубконто) и имена их полей, ошибки типов, контекст вызова (клиент/сервер), существование методов
   платформы, корректность НаборЗаписей.Отбор и Записать(Истина).
2. Логика: <конкретные сценарии из контекста / доп. фокуса — пустые значения ключа, границы периода, повторная
   загрузка, задвоение сумм при соединении неагрегированных таблиц, влияние на соседние ветки механизма>.
3. Производительность: число обращений к СУБД, индексы, размер временных таблиц.
4. Транзакционность: что останется в данных при обрыве в середине.
5. Регламент проекта из CLAUDE.md, если есть (где разрешено править, запрещённые конструкции, формат комментариев).

ФОРМАТ ОТВЕТА (на русском):
- Находки по критичности: Высокая / Средняя / Низкая (или уровни из регламента проекта, например BLOCK / WARN).
- Для каждой: файл и номер строки, суть в одном предложении, конкретный сценарий сбоя, точечная правка.
- Возможные ложные срабатывания помечай «(проверить: …)». Отделяй ошибки от стиля.
- Не предлагай переписывание модуля целиком. Критичных проблем нет — так и напиши.

ОГРАНИЧЕНИЯ: только анализ. Ничего не создавай и не изменяй на диске.
<блок журнала из Шага 3, если это повторный прогон>
<доп. фокус текстом, если задан>
```

## Шаг 5. Запуск

```powershell
# edt: -WorkDir = корень рабочей области EDT
powershell -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>\scripts\codex-review.ps1" `
    -Mode edt -WorkDir "<корень>" -PromptFile "<workdir>\_prompt.txt" -Effort <effort>

# offline: -WorkDir = <workdir> с материалами
powershell -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>\scripts\codex-review.ps1" `
    -Mode offline -WorkDir "<workdir>" -PromptFile "<workdir>\_prompt.txt" -Effort <effort>
```

Раннер сам находит свежий `codex.exe`, запускает `codex exec --ignore-user-config --sandbox read-only`,
подаёт промпт через stdin из файла и пишет ответ в `<workdir>\_review.md`.

- На `medium`/`high` ревью занимает 2–15 минут — запускать **в фоне** (`run_in_background: true`), не ждать в
  foreground: потолок foreground-вызова инструмента короче сторожа раннера.
- Сторож: через `-TimeoutSec` (по умолчанию 900) Codex и его дочерние процессы принудительно завершаются.
  300 с на объект с большим модулем не хватает — Codex успевает только прочитать файлы.
- Код 0, но ответа нет (`_review.md` не создан или пуст) — Codex не ответил вообще: исчерпан лимит, «at capacity»,
  слетела авторизация. Раннер считает это ошибкой и печатает хвост лога (`_codex_stderr.log`). Не выдавать
  пустоту за «замечаний нет»; при лимите — сказать пользователю, когда он снимется, и повторить позже.
- Не перенаправлять вывод раннера через `2>&1` в Windows PowerShell: строки Codex в stderr превращаются в
  `NativeCommandError` (`*> лог-файл` — можно).
- Песочница Windows: при `[windows] sandbox = "elevated"` в конфиге Codex блокирует любой подпроцесс, даже чтение
  файлов («blocked by policy»). Раннер всегда передаёт `-c 'windows.sandbox="unelevated"'`, запрет записи
  сохраняется. Ошибки `MethodInvocationNotSupportedInConstrainedLanguage` в логе — норма: Codex сам переходит на
  простые команды.

## Шаг 6. Возврат результата

- Прочитать `_review.md`, вернуть находки пользователю **дословно**.
- Шапка: режим, объект(ы), база сравнения (offline: какой бэкап или «без диффа»), область (правки / `--all`),
  итерация журнала, effort, время.
- По **каждой** находке дать свой вердикт: чинить / отклонить (с причиной) / вынести на решение пользователя.
  Codex не знает контекста данных — его уровень критичности не окончательный.
- Предупреждение: **находки не верифицированы**. Codex видит только код — не видит данные и не выполняет запросы.
  Перед правками:
  1. проверить каждую находку фактами (метаданные, соседний код, исходники БСП/типовой конфигурации, реальные данные);
  2. отделить дефекты от задуманного поведения — искать рядом авторские комментарии, совпадение с образцом в проекте;
  3. сценарии проверять на данных (посчитать строки/документы/суммы), а не рассуждением;
  4. доложить раздельно: подтвердилось / снято фактами (почему) / оставлено осознанно.
- Обновить журнал `review.md` (Шаг 3): новые находки, статусы прежних по вердикту этого прогона.
- Сам Codex ничего не правит; правки по находкам — отдельным шагом, по правилам проекта.

## Типичные ошибки при подготовке

- Промпт передан аргументом PowerShell — кириллица превращается в мусор (промпт только файлом).
- Кириллица в имени `<workdir>` — Codex не читает файлы (offline).
- `context.md` без BOM — Codex видит мусор вместо кириллицы (offline).
- Дифф без нормализации CRLF/LF — весь файл выглядит изменённым, ревью уходит в пустоту (offline).
- Передан только изменённый файл без диффа и без формата маркеров — Codex ревьюит весь модуль.
- Повторный прогон без журнала — те же замечания по кругу или пропуск непочиненного.
- edt: передано имя объекта, которое есть и в конфигурации, и в расширении, — ревью не того объекта.
- Не описана механика вокруг правки — находки общие и бесполезные.

## Окружение (CRLF/BOM)

`awk`/`sed` в Git Bash при перезаписи файла теряют `\r`: CRLF → LF/смешанный. Файлы 1С (выгрузка Конфигуратора и
модули EDT) — UTF-8 с BOM и CRLF; `Template.xml` макетов выгрузки хранится без финального перевода строки.
Проверка: число `\r` должно равняться числу `\n`.

## Файлы

- `scripts/codex-review.ps1` — раннер Codex (`-Mode`, `-WorkDir`, `-PromptFile`, `-Effort`, `-OutFile`, `-Model`, `-TimeoutSec`).
- `scripts/edt-resolve.mjs` — резолвер пути из дерева EDT в папки объектов (режим edt; нужен Node.js).
