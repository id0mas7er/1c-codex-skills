# MCP Toolkit для 1С — как работать и где грабли

Toolkit = внешняя обработка `MCP_Toolkit.epf`, запущенная **внутри клиента 1С**; кнопка «Запустить сервер» поднимает HTTP-сервер на 127.0.0.1:<порт>. Поэтому:
**нет открытого клиента 1С (или не нажата кнопка) = нет Toolkit.** Все остальные проблемы — следствие этого.
Справка по параметрам эндпоинтов: скилл `calling-1c-rest-api-via-curl` (там же REST через curl). Здесь — только опыт и ловушки.

## 0. Базовые правила
- Данные баз 1С читать через Toolkit (`mcp__1c-*` или его REST), а не через COM-соединение и прочие обходы, если пользователь не решил иначе.
- Боевая база — только чтение: `execute_query`, `get_metadata`, `get_event_log`… `execute_code` с записью, `restart/close_1c_session` — только по слову пользователя. В тестовой базе писать можно, но защиту Toolkit снимать только по п. 4.
- Токен Toolkit не записывать в файлы и не повторять в ответах. Токен в заголовке `Authorization: Bearer` нужен, только если задан в форме.
- Разрешения, данные для одной базы («анонимизация не нужна», «запись разрешена»), на другие базы и проекты не переносить — спросить.

## 1. Какая сервер = какая база (проверять всегда)
Порты назначаются **на базу** и могут меняться между сессиями (6003 сегодня БП, завтра ЕРП). Имя MCP-сервера (`1c-bp`, `1c-erp` …) ничего не гарантирует.
- Первый вызов в сессии: `get_metadata` без параметров → смотреть `configuration.metadata.Синоним`/версию. Только потом работать.
- Если нужной базы нет среди серверов: сам `claude_desktop_config.json` не править — попросить пользователя добавить сервер / сменить порт в форме Toolkit.
- Два Toolkit на одном порту не уживаются: пока одна база держит порт, вторая не поднимется. Пользователю — «Остановить сервер» → сменить порт/токен → «Запустить».

## 2. Подключение: падает и само не поднимается
- Закрыли/перезапустили клиент 1С (в т.ч. `tc_session stop_client`, импорт через ibcmd, авария) → в сессии MCP `1c-*` уходит в `failed`/`ECONNREFUSED`/`Server 1c-xxx unavailable`/`Session terminated`.
- `reconnect_session_connector` его **не берёт** («already connected» / не connector). Переподключает только пользователь: `/mcp` → сервер → Reconnect. Если сессия стартует при уже поднятом Toolkit — подключится само.
- Не перезапускать сервер в форме Toolkit без нужды: после каждого перезапуска связь восстанавливается заново.
- **Обход без `/mcp`:** REST напрямую, он от MCP-сессии не зависит: `curl -s --noproxy 127.0.0.1 http://127.0.0.1:<порт>/health` (живость; без токена), `POST /api/execute_query` с JSON. Токен нужен, только если задан. Проверка MCP-эндпоинта: `/mcp` → 401 или 406 = сервер жив (406 без токена значит, что токен не проверяется).
- «Сервер запущен, но клиент закрыт» не бывает: после закрытия клиента порт свободен — искать клиент (`tasklist | findstr 1cv8`), а не чинить MCP.
- Поднять Toolkit самому: `tc_session launch_client` (**тонкий `1cv8c.exe`**, толстый падает) с `extra_args=["/Execute","...\MCP_Toolkit.epf"]`, затем `tc_find find_objects title="*сервер*" scope=application` → `tc_field click` на «Запустить сервер». `wait_for_object_displayed` по имени кнопки виснет. Первый запуск после `apply` иногда виснет без окна — kill и заново.
- Чужой клиент пользователя закрывать нельзя; свой (поднятый testpilot'ом) — можно.

## 3. Таймауты и «занято»
- `Request timed out` (≈180 с прокси): код/запрос дольше лимита. **Внутри 1С обработка при этом, скорее всего, продолжается** — не слать повтор вслепую (двойная запись/двойная нагрузка). Длинное делать так: код пишет результат в файл (`ЗаписьТекста`) и сразу возвращает `Результат = "запущено"`; читать файл потом. Для REST ставить `curl --max-time 200`.
- Пока Toolkit выполняет долгий шаг, он **не принимает новых запросов** (однопоточный клиент 1С). Ждать завершения/файла результата, не слать параллельно.
- Модальное окно в клиенте (вопрос, ошибка, «Завершить работу?») тоже подвешивает ответы → смотреть скриншот/`tc_app get_active_window`.
- Фоновые задания, которые заполняют формы, могут быть ещё не завершены — см. `ФоновыеЗадания.ПолучитьФоновыеЗадания`.

## 4. Защита `execute_code`: «опасные ключевые слова» (403)
Фильтр по подстроке в тексте кода отклоняет вызов: `Операция запрещена: код содержит опасные ключевые слова: Записать` (бывает `Удалить`, `Выполнить`, `УстановитьПривилегированныйРежим`, `Записать`…). Список — в ответе (`dangerous_keywords`).
- Снимается галочкой «Автоматически разрешать операции: Записать» (`ФлагАвтоЗаписать`) в форме Toolkit клиента. **Включать только после короткого вопроса пользователю («включу запись на один вызов для …?»), после вызова выключить и сказать об этом.** Это защитный механизм, не баг.
- **Не обходить** фильтр (код из файла через `Выполнить(Код)`, склейка слов и т.п.) — фильтр проверяет только текст вызова, и такой обход обесценивает защиту пользователя.
- Слова ищутся по подстроке, поэтому ложные срабатывания возможны (например в комментарии/строке `"...Записать..."`) — переформулировать текст, а не отключать защиту.
- Классификатор авто-режима Claude Code может отдельно блокировать `mcp__1c-*__execute_code` («Modify Shared Resources», «judged dangerous») или отвечать «no verdict (error)»: повторить 1 раз как есть, потом спросить пользователя. Не искать обходов.
- Если нужна запись: проводки/документы — `Док.Записать()` затем `Док.Движения.<Регистр>.Записать()` (для `ОперацияБух` без проведения; у нового объекта набор без регистратора не сохранится); проверять ограничения реквизитов (`ДатаОкончания` ≥ начала и т.п.).

## 5. Формат execute_code и execute_query
- В `execute_code` результат — переменная **`Результат`**; возвращается только она (это же то, что видит анонимизатор). `Сообщить`/`Message` не возвращается.
- Код выполняется через `Выполнить()` — ошибки приходят как `Ошибка при вызове метода контекста (Выполнить): {(строка, колонка)}: …` с маркером `<<?>>` в тексте запроса там, где разбор споткнулся. Читать маркер, а не угадывать. Номер строки считается внутри кода.
- Ошибка в `Новый Запрос(...)` внутри `execute_code` иногда приходит как `success:true` с полем `"Ошибка…"` в `data` — проверять содержимое, а не только `success`.
- Типичные ошибки запросов (все — по метаданным конкретной базы, **не по памяти типовой конфигурации**): `Поле не найдено` (в логах это самая частая ошибка: поля регистров бухгалтерии/ПВХ в БП, ERP и ЗУП называются по-разному, напр. `СубконтоДт1` на таблице движений не нашлось — сверять с `get_metadata`), `Таблица не найдена`, `Поле не входит в группу`, `Не задано значение параметра` (параметр `&П` запроса не передан), `Ожидается имя`/`Синтаксическая ошибка` (часто зарезервированное слово как псевдоним: `Дт`, `Кт`, `Тип`, `Ссылка` — переименовать).
- Перед сложным запросом: `get_metadata filter="Документ.X"` (реквизиты, ТЧ, измерения), `attribute_mask` для поиска реквизита по всей базе. У полей составного типа `Тип` усечён до 20 типов — полный список через `filter` на одно поле и `types_offset`.
- Ответ по умолчанию в формате TOON (строка в `data`), не JSON; лимит строк у `execute_query` задаётся параметром, у больших выборок есть `truncated`/`has_more` — не принимать усечённый результат за полный.
- `УстановитьПривилегированныйРежим` фильтр тоже блокирует (видно в логах) — для чтения не нужен.

## 6. Анонимизация и файлы
- Анонимизатор (вкладка «Анонимизация» в форме Toolkit) подменяет ФИО/названия/ИНН токенами вроде `[ORG-00030]` **только в ответе инструмента**. Токены **разные в разных сеансах** → сопоставлять документы между сеансами/базами по ним нельзя. Для сверки между базами — писать данные в файлы (`ЗаписьТекста` → `.tsv`) и читать файл обычным чтением: он идёт мимо MCP и мимо анонимизатора.
- Это обходит анонимизацию: запись файлов не входит в «опасные» операции. Делать так можно только с разрешения пользователя для данной базы. Подтверждено: `[ORG-xxxx]` в тексте ошибок — тоже токены, а не реальные значения.
- Кодировка файла: `КодировкаТекста.UTF8`; в логах была ошибка «Поле объекта не обнаружено (UTF8)» при неверном имени перечисления кодировки — проверять синтаксис в `get_bsl_syntax_help`.
- Пути для записи — только существующие каталоги, временный каталог пользователя подходит.

## 7. Ловушки в окружении
- Файловая база: `ibcmd import` требует монопольной блокировки — клиент (и Toolkit) закрыть до импорта, дождаться пустого `tasklist | findstr 1cv8`; потом поднять клиент и Toolkit заново, `/mcp` Reconnect.
- Пароль пустой в `ibcmd`: `--password=` через `cmd /c`, иначе ждёт ввод и «висит».
- Скрипты .ps1 с кириллицей сохранять с BOM. В PowerShell `curl` — алиас `Invoke-WebRequest`: использовать `curl.exe` или Bash; кириллицу в теле лучше передавать из файла (`--data-binary @q.json`, UTF-8) — *не проверялось в логах, предосторожность*.
- Версия платформы клиента = версия `1cv8c.exe` ; указывать её явно в `launch_client`.
- UI-проверки после загрузки расширения: первое заполнение может пройти **без расширения**; ждать завершения фонового задания; принимать «изменение ожидаемого текста», а не «ошибок нет».
- Обновление расширения/отчёта в базе не видно в уже открытом клиенте — перезапуск клиента (и Toolkit) обязателен.

## 8. Чек-лист перед работой
1. `curl http://127.0.0.1:<порт>/health` или `get_metadata` — какая база и жива ли.
2. Не жива → есть ли процесс клиента 1С; нажата ли «Запустить сервер»; порт тот ли; затем просить `/mcp` Reconnect или идти по REST.
3. Чтение — свободно; запись/закрытие сессии/снятие защиты — вопрос пользователю.
4. Длинное — через файл результата, без повторов при таймауте.
5. Данные между базами — файлами, только если разрешено; не сопоставлять по анонимным токенам.
6. Схему брать из `get_metadata` базы, а не из памяти о типовой конфигурации.
