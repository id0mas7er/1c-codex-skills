# /codex-test-1c — тестирование 1С силами Codex + 1c-testpilot

Codex (`codex exec`) получает промт тестирования, сам запускает тест-клиент 1С через MCP-сервер
`1c-testpilot`, проходит сценарии и пишет отчёт. Claude запускает Codex, ждёт завершения,
разбирает отчёт, **проверяет каждую находку по коду** и исправляет дефекты.

Ниже `<SKILL_DIR>` — каталог этого скилла (там лежит `scripts/`).

## Предусловия (проверить ДО запуска)
1. Пользователь загрузил в базу актуальную версию расширения/конфигурации. Не выяснено — спросить.
2. Нет «висящих» тест-клиентов на этой базе:
   `Get-CimInstance Win32_Process -Filter "Name='1cv8.exe' or Name='1cv8c.exe'"`, ищем `/TESTCLIENT`.
   Процессы пользователя (Конфигуратор, его сеансы) НЕ убивать — только сообщить.
3. Промт тестирования (`.md`) самодостаточен: база, пользователь, версия платформы, сценарии
   с ожидаемым результатом, **путь файла отчёта**, куда класть скриншоты и тестовые файлы.
   Если в базе нет данных для сценария (пустые справочники и т. п.), в промте описан обход:
   копирование существующих документов. Шаблон — `examples/prompt-template.md` в репозитории.
4. Отчёт предыдущего прогона не должен перезаписываться: у нового файла отчёта свой суффикс (`_повтор`, `_2`…).
5. В `~/.codex/config.toml` есть секция `[mcp_servers.1c-testpilot]` (раннер проверяет сам: `PREFLIGHT FAIL` в `status.txt`).
   Обновление Codex может её стереть — вернуть так (пути прямыми слэшами, чтобы не мучиться с экранированием):
   ```toml
   [mcp_servers.1c-testpilot]
   command = "C:/Users/<user>/.local/bin/1c-testpilot.exe"
   args = ["--env-file", "<путь к каталогу testpilot>/.env"]
   startup_timeout_sec = 60
   ```
   Это постоянная правка конфига пользователя — с его согласия и с копией `config.toml.bak_<дата>`.
6. В промте `launch_client` вызывается с **`exe` и `version` той платформы, на которую есть лицензия**
   (например `exe="C:\Program Files\1cv8\<версия>\bin\1cv8c.exe", version="<версия>"`). Без них testpilot берёт
   `TC1C_PLATFORM_EXE` из своего `.env` — если на ту версию нет лицензии, появится окно «Лицензия не обнаружена», прогон стоит.
7. В промте НЕ запрещать «JavaScript / `tools.*`» — это и есть рабочий путь вызова MCP (см. ниже).

## Порядок
1. **Рабочий каталог** — каталог во временной папке сессии, например `<scratchpad>\codex-test-<слаг>`, **полным путём**
   (`C:\Users\<Имя>\…`, кириллица допустима). Короткий 8.3-путь (`C:\Users\ABCD~1\…`, так часто выглядит `%TEMP%`) нельзя:
   песочница отказывает всем командам и записи файлов (`cannot enforce split writable root sets`), раннер такой путь не примет.
   Не использовать каталог, где лежит чужой `AGENTS.md`: Codex подхватит его инструкции.
2. **Пробный запуск** (~1 мин), проверяет, что MCP-вызовы проходят:
   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>\scripts\run-codex-test.ps1" -WorkDir "<WorkDir>\probe" -Probe
   ```
   В `<WorkDir>\probe\last_message.md` должен быть ответ `list_profiles` (`ok: true`), в `status.txt` — `TESTPILOT_CALLS` > 0.
   Если там отказ или ошибка, до полного прогона не переходить, см. «Подводные камни».
   **Пробник проверяет не всё:** короткий промт проходил и тогда, когда полный падал. Перед полным прогоном
   полезна вторая проверка — преамбула + только первый абзац промта («выполни только list_profiles и заверши»).
3. **Полный прогон — отдельным процессом.** Фоновая задача инструмента обрывается примерно через 10 минут, а прогон идёт 20–60 минут:
   ```powershell
   $p = Start-Process powershell.exe -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File',
     '<SKILL_DIR>\scripts\run-codex-test.ps1','-PromptFile','<промт.md>','-WorkDir','<WorkDir>','-AddDir','<каталог отчёта>' `
     -WindowStyle Hidden -PassThru; "PID $($p.Id)"
   ```
   `-AddDir` — каталоги, куда Codex разрешено писать отчёт и скриншоты (кроме `WorkDir`).
   Преамбула `scripts/preamble.md` дописывается к промту автоматически. В ней: неинтерактивный режим, полномочия,
   закрытие окон авторизации «Отменой», **правило трёх попыток на шаг**, ⛔ только для воспроизводимого,
   частичный отчёт при обрыве.
4. **Ожидание — Monitor**, `timeout_ms` = 1800000 (30 мин). Скрипт ждёт `EXIT` в `<WorkDir>\status.txt`
   или исчезновения процесса по PID. По истечении срока — перевзвести. Не опрашивать через sleep.
   Процесс записывает `EXIT` и сразу завершается, поэтому, увидев «процесс исчез», **перечитай `status.txt`**:
   `EXIT 0` там означает штатное завершение, а не сбой. **Но `EXIT 0` + `TESTPILOT_CALLS 0` (или прогон кончился
   за 1–2 минуты) = Codex до 1С не дошёл** — читать `last_message.md`, а не ждать отчёт со сценариями.
   Полезно в мониторе через 2–3 мин вывести число строк `^mcp: 1c-testpilot` в `stderr.log` (UTF-16 → `iconv -f UTF-16`)
   и путь exe процесса с `/TESTCLIENT` — так сразу видно, пошёл ли прогон и на какой платформе. Пример цикла:
   ```bash
   while true; do grep -q EXIT "$S" && { grep EXIT "$S"; break; }
     tasklist //FI "PID eq $PID" | grep -q $PID || { sleep 2; grep EXIT "$S" || echo "GONE without EXIT"; break; }
     sleep 30; done
   ```
5. **Разбор результата:**
   - прочитать `last_message.md` и файл отчёта; при сбое смотреть `stderr.log`
     (пишется в UTF-16 от PowerShell, читать через `Get-Content -Encoding Unicode`);
   - каждую ⛔ проверить по коду и метаданным: воспроизвести логику, найти причину. Codex может ошибаться,
     например принять поведение платформы за дефект;
   - ⚠️ из-за данных или окружения (нет данных в базе, модальные окна) не выдавать за дефекты кода;
   - подтверждённые дефекты — исправить по правилам проекта (бэкап, комментарии-шаблоны, валидаторы, линтер),
     затем при необходимости повторить только затронутые сценарии;
   - формулировать статус честно: «исправлено в коде, в базе не проверено» ≠ «проверено».
6. Итог записать в заметки проекта: что проверено, дефекты и причины, путь к отчёту.

## Подводные камни (codex-cli 0.155)
- **`MCP tool call requires approval, but approval policy is never`** — без
  `-c mcp_servers.1c-testpilot.default_tools_approval_mode="approve"` любой MCP-вызов в `exec` отклоняется.
  Раннер ставит этот флаг. `--dangerously-bypass-approvals-and-sandbox` НЕ использовать.
- **`--ignore-user-config` нельзя**: MCP-сервер `1c-testpilot` подключён в `~/.codex/config.toml`.
- **Песочница Windows `elevated`** (если стоит в `config.toml`) блокирует подпроцессы. Раннер ставит `windows.sandbox="unelevated"`.
- **PowerShell 5.1** читает `.ps1` без BOM как ANSI, а в путях кириллица. Все `.ps1` скилла — UTF-8 с BOM.
- **Правила «три попытки» в инструкциях Codex нет**, оно задаётся только преамбулой. Без него агент либо
  застревает на шаге, либо бросает весь прогон.
- **`no active window` сразу после `launch_client`.** Две причины: окно входа «Доступ к информационной базе»
  (в промте нет `user=` для `launch_client`) или долгая заставка «Загрузка конфигурационной информации» при первом
  запуске после обновления расширения. В промте всегда давать `launch_client(..., user="<пользователь>")`; преамбула велит ждать заставку.
- Модель и уровень рассуждений раннер задаёт сам: по умолчанию `gpt-6-luna` и `max` (`-Model`, `-Effort` — переопределить).
  Значения из `~/.codex/config.toml` для них не используются.

## Подводные камни (codex-cli 0.160)
- **`Error loading config.toml: invalid transport in mcp_servers.1c-testpilot`** — секция сервера пропала из
  `config.toml` (обновление Codex/синхронизация переписали файл). Флаг `default_tools_approval_mode` создаёт секцию
  без `command` → «invalid transport». Лечение — вернуть секцию (предусловие 5). Подключение сервера только флагами
  `-c mcp_servers.1c-testpilot.command=...` НЕ годится: пробник работает, а в длинном прогоне инструмента нет.
- **Как Codex 0.160 вызывает MCP.** Прямого слота инструмента нет: вызов идёт через мост exec (code mode) —
  `tools.mcp__1c_testpilot__tc_session({...})` (дефис в имени сервера → `_`). Преамбула и промт должны называть
  именно этот способ. Фраза «не через JavaScript/`tools.*`» запрещает рабочий путь: модель уходит в `cua_repl/js`,
  где реестра MCP нет → `TypeError: tools.mcp__1c_testpilot__tc_session is not a function`.
- **`cua_repl` (плагин `unified-computer-use@openai-bundled`) — конкурент моста.** Раннер выключает его на запуск.
  `mcp_servers.node_repl.enabled=false` не помогает (это другой сервер), `features.code_mode_host=false` — вредно:
  через тот же мост работают `exec_command`/`apply_patch`, отчёт не записать («code-mode host is disabled»).
- **`is not a function` может быть и гонкой старта сервера** (тот же промт в одном прогоне проходит, в следующем — нет).
  Преамбула велит ждать ~20 с и повторять до 3 раз.
- **Платформа.** Версия в `connect` обязана совпадать с запущенной: «Различаются версии клиента и сервера (X - Y)».
- **Где смотреть, что видела модель:** `%USERPROFILE%\.codex\sessions\YYYY\MM\DD\rollout-*.jsonl`
  (`McpToolCall server=1c-testpilot` — успех; `server=cua_repl` — ушла не туда).
- **Claude как запасной вариант:** у Claude может быть свой `1c-testpilot` (`mcp__1c-testpilot__tc_*`, см. README),
  но его stdio-соединение на длинных прогонах рвётся («Connection closed») — для длинного прогона надёжнее Codex по этой схеме.
- Агент может отказаться нажимать кнопки в окнах внешних интеграций (Документооборот и т. п.).
  Преамбула прямо разрешает «Отмену», но если отказ повторится, это ⚠️ окружения, окно закрывает пользователь.
